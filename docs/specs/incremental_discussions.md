## 一、判定与口径层（Increments 01–13）

### I-01 `trigger_type` 多口径判断｜**纯新增**｜P0

**决议**：Adapter 向 Core 发请求时必须携带 `trigger_type`，枚举四值：

| 值 | 含义 | 处理口径 |
|---|---|---|
| `user_msg` | 用户说话 | 正常走双轨判定，全额计分 |
| `proactive` | Bot 主动找事 | 按「它自己的心意」判定，不按「被影响」判定 |
| `cron_task` | 定时任务干活 | 按「干活时的心情」判定，不计入用户情感账 |
| `runtime_context` | 宿主塞入的上下文 | **直接跳过情绪计算**：不记账、不注入、不进状态机 |

**边界条件（死线）**：`trigger_type` **必须在请求进入时就确定**，不允许事后推断。
理由原文：判错口径会让理由完全相反——「它自己来找你」被当成「被叫起来干活」。
**出处**：#19 #20 #21 #51

### I-02 `intent_type` 意图分流｜**纯新增**｜P0

**决议**：`evaluate_track_a()` 内新增三分类：

| 值 | 判据 | 处理 |
|---|---|---|
| `noise` | 纯数字、单字符（len<3 且无情感）、无意义乱码 | `target=50`，`path="noise"`，**不触发情绪更新** |
| `emotion` | 命中正负情感词典 | 正常打分 |
| `unknown` | 未命中词典的普通文本 | 交 Track B 或取中性 |

**配套死线**：`path=="noise"` 时，`PromptBuilder` **绝对禁止**输出讨好型语句（如「知道了」「呜，本鲸鱼知道了」），必须输出符合人设的短句。
**背景缺陷**：输入「6」「123」曾被误判为正向并输出严重 OOC 回复。
**出处**：#57 #62 #19

### I-03 Track B 置信度门槛｜**纯新增**｜P0

**决议**：Track B 必须返回 `{"emotion_target": int, "confidence": float, "reason": str}`。
`confidence < 0.6` 时：**不注入 OS，只更新内部状态**，后台日志留痕 `[DEBUG] Low confidence, ignoring OS injection`。

**与 I-02 的差异（易混）**：I-02 拦的是「Track A 判不出方向」，I-03 拦的是「Track B 判了但没底」。两者是串联关系，不是替代关系。
**出处**：#20 #21 #123

### I-04 负面原因白名单｜**纯新增**｜P0

**决议**：Track B 判负时**必须**给出 `reason`。代码层硬拦截：

- **允许扣分**的原因仅三类：**心疼**、**担心**、**它自己难过**
- **否决或减半**的原因：涉及「被冒犯」「被惹怒」「被无视」等
- 日志：`[WARN] Emotion drop rejected by reason whitelist`

**设计意图原文**：「心情下降的唯一合法理由是心疼、担心或它自己难过，绝不许因为『你惹它生气』」——这是防记仇的代码级落点，不是提示词层的自我约束。
**出处**：#20 #21 #19

### I-05 突变拦截器｜**纯新增**｜P1

**决议**：满足任一条件时**跳过平滑公式**，直接输出 `[状态：需LLM自主判断]`：

1. `|S_本轮 - S_上轮目标| > 40`
2. 文本包含 `["其实", "但是", "不过"]`

**解决的痛点**：单轮限幅 ±5 会导致「上一秒哈哈大笑、下一秒说『其实我想哭』」时情绪慢吞吞地降，反应慢半拍。
**与计划第 30 条（动态平滑限幅）的关系**：是**例外通道**，不是替代。
**出处**：#125

### I-06 换标签迟滞（Hysteresis）｜**纯新增**｜P1

**决议**：等级标签切换需要**超过额外强度阈值**才允许发生，而非仅跨过边界值。
例：L1→L2 需要跌到 32 以下（而非 35 以下）；L2→L1 需要升到 38 以上（而非 35 以上）。
**目的**：防止在临界值附近反复横跳，导致内心 OS 和行为不稳定。
**出处**：#63 #64

### I-07 转折/反讽标记词表｜**细化**｜P0

**决议**：检测 `其实 / 不过 / 但是 / 呵呵 / 行吧 / 随便` 时打上 `semantic_conflict = true`，**强制豁免关键词定分**，转交 Track B。
**与计划第 27 条（Track B 触发条件）的关系**：把「转折冲突」从模糊描述变成了**可枚举的词表**。
**出处**：#124

### I-08 否定翻转与降级兜底｜**细化**｜P1

**决议**：文本含否定词（「不」「没」）但打出极低分时，执行 `score = 50` 降级兜底，或不更新 `window_scores`。
**出处**：#128

### I-09 白名单物理短路｜**细化**｜P0

**决议**：`if user_id in ADMIN_WHITELIST` **必须是判定逻辑的第一行代码**，在词典匹配之前。
**反例（禁止）**：把白名单判断写在词典匹配之后 → 管理员说了句骂人的话会先触发负面情绪再判白名单，数值被误扣。
**出处**：#86 #87 #117 #121

### I-10 Track B 输出格式强约束｜**细化**｜P0

**决议**：

- 强制 JSON Mode；框架不支持时用正则提取
- 提取失败默认返回 `{"emotion_target": 50, "confidence": 0}`
- Prompt 极简（< 150 Token），输入为「代码信号 + 最近 2~3 轮片段」
- 可选字段 `dominant: "sad|happy|neutral|conflict"`

**出处**：#120 #121 #124

### I-11 双通道语义判定｜**远期 P3**｜不入本期

**决议**：用本地小模型分别读「思考/内心」与「正文/说出口的话」，区分「口是心非」与「真心实意」。
**处置**：工程改动过大，列为 P3 远期，不进 V5.0 范围。
**出处**：#63

### I-12 本地轻量分类器替代词典｜**P2**｜不入本期

**候选**：`distilbert-base-uncased-go-emotions-onnx`（约 65 MB），完全离线、毫秒级、能识别反讽与混合情绪。
**处置**：P2 后续迭代。V5.0 仍用词典 + Track B 双轨。
**出处**：#63

### I-13 情绪分布输出（而非单值）｜**P2**｜设计储备

**决议**：长期方向是不输出「当前情绪=开心」，而输出「开心 0.6 / 平静 0.3 / 轻微不安 0.1」的分布。
**原则**：情绪机只输出**建议性状态分布**，不决定具体表达。
**处置**：与当前 `emotion_score: int` 单值模型不兼容，需数据模型升级，列为 P2。
**出处**：`优化计划/情感算法优化.txt` 第 1 节

## 二、状态与衰减层（Increments 14–24）

### I-14 情绪基线 50 → 70｜**修正**｜P1

**计划原文**（第 32 条）：「自动使情绪值随时间向中性（**50 分**）缓慢回归」。
**决议**：基线改为**可配置的 70**（默认偏积极）。
**理由**：一只健康活泼的 Bot 不该长期处于 50 分的冷漠状态。
**注意**：`NEUTRAL_TARGET` 与 `BASELINE` 是两个不同常量——中性判定值仍为 50，**衰减回归目标**改为 70。二者不可混用。
**出处**：#19 #20 #21

### I-15 半衰期参数｜**细化**｜P1

**决议**：

- 情绪总分向基线回归：**半衰期 ≈ 3 小时**
- 具体情绪维度向 0 衰减：**半衰期 ≈ 90 分钟**
- 负面情绪（E < 基线）衰减速率 **× 0.5**（让难过留得更久）

**出处**：#19 #20 #21 #66

### I-16 负向偏差（Negativity Bias）｜**细化**｜P0

**计划原文**（第 34 条）：「负面情绪的衰减速率是正面情绪的 0.5 倍」——**已覆盖**。
**增量**：明确判据为 `E < 50`（不是 `E < 基线`），且该系数与 `resilience` 性格向量相乘调制。
**出处**：#46 #66

### I-17 性格向量四维｜**纯新增**｜P1

**决议**：从 `persona.txt` 一次性提取 0.0~1.0 的四维向量，存本地（SQLite 或配置），**不每轮调用 LLM**：

| 维度 | 调制作用 |
|---|---|
| `neuroticism` 神经质/敏感度 | 高则负面情绪放大 |
| `extraversion` 外向性 | 高则正向表达更积极 |
| `agreeableness` 宜人性/柔软度 | 高则容易原谅 |
| `resilience` 韧性 | 高则负面情绪衰减越快 |

**缓存死线**：性格参数必须持久化，**不允许每次对话读取或调用 LLM 重算**——既保护前缀缓存又减少延迟。
**出处**：#57 #58

### I-18 性格调制公式｜**纯新增**｜P1

```
delta = clamp(0.2 * (target - E_prev), -5, 5)
if target < 50:  delta *= (1.0 + neuroticism * 0.5)
else:            delta *= (1.0 + extraversion * 0.3)
```

**出处**：#57

### I-19 情绪饱和（习惯化）｜**细化**｜P1

**计划原文**（第 36 条）：「短时间连续受到同频刺激，情绪增量递减」——已覆盖。
**增量**：递减系数由 `resilience` 调制，且 `_habituation_alpha` 读的是 `persona_traits` 而非硬编码。
**出处**：#57

### I-20 概率解禁参数｜**细化**｜P0

**计划原文**（第 51 条）：「维护连续刺激计数器，高连击时按概率解除人设防线」——方向已覆盖。
**增量（具体参数）**：

```
stimulus_counter：5 分钟内同极性连续刺激 +1，否则重置
unlock_probability = min(0.9, 0.10 + counter * 0.15)
触发条件：counter >= 3 AND random() < unlock_probability
```

**性格加成**：`agreeableness` 较低（傲娇属性）时，受连续夸奖的解禁概率额外加成。

**出处**：#57 #59

### I-21 解禁 ≠ 解除安全限制｜**死线**｜P0

**决议**：`SubconsciousAuditor` 中**规则硬拦截（Rule-based block）必须写在概率解禁之前**。
解禁只允许解开「傲娇/嘴硬/冷淡」的**人设限制**，绝不解除 NSFW / 政治 / AI 暴露等底层安全限制。
**出处**：#57（避坑指南第 1 条）

### I-22 解禁指令的注入位置｜**死线**｜P0

**决议**：`override_directive` 必须放在最终 Prompt 的**最末尾（用户消息之后）**。
理由：模型对越靠后的指令遵循度越高，放前面会「继续端着架子」。
**出处**：#57（避坑指南第 2 条）

### I-23 情绪显著性记忆联动｜**细化**｜P1

**计划原文**（第 72 条）：「写入记忆时附带情绪权重，防止重要回忆被轻易 LRU 淘汰」——方向已覆盖。
**增量**：`emotion_level ∈ {L2, CRISIS}` 时，记忆条目 `salience = 1.0` 并 **Pin**，不受 7 天 TTL 与 200 条 LRU 影响。
**出处**：#57 #61

### I-24 无变化不记账｜**纯新增**｜P1

**决议**：`delta` 为 0 或极小值时**跳过数据库写入**，只更新内存态。
**目的**：减少 I/O，同时避免「时间线被无意义的记录灌满」。
**出处**：#19 #20

## 三、隔离与一致性层（Increments 25–33）

### I-25 `(user_id, chat_scope)` 复合主键｜**修正**｜P0

**计划原文**（第 100 条）：「群聊/私聊 ID 隔离：私聊 group_id 传 None，防群冷却误伤私聊」——**只覆盖了冷却池**。
**决议**：情绪状态本身也必须按 `(user_id, chat_scope)` 隔离，`UserState` 主键改为复合键。
**`chat_scope` 取值规则**：群聊 `g:<group_id>`，私聊 `p:<user_id>`（与撤回冷却池键格式一致）。
**现状**：冷却键已隔离，情绪状态仍共用。
**出处**：#11 #1

### I-26 「锚点全局、情绪分房、理由分房」｜**修正**｜P0（原 P1，已上调）

**决议**：分三层，各归各的表——

| 层 | 载体 | 主键 | 分房 | 变化速度 |
|---|---|---|---|---|
| 关系锚点 | `UserAffinity` | `user_id` | ❌ 全局 | 慢（deltas 累积 + compaction） |
| 场景情绪 | `UserState.emotion_current` | `(user_id, chat_scope)` | ✅ **严格** | 快（±5/轮） |
| 整体心情 | `BotMood` | `id=1` | ❌ 全局单行 | 最慢（阻尼 0.08） |

**必须按 `chat_scope` 物理隔离的三项**：

1. `UserState.emotion_current`（场景情绪，见 I-25）
2. **连续刺激计数器**（`auditor._stimuli`）
3. **记忆条目**（`memory_router.memories`，含原始消息全文）

**`chat_scope` 取值**：群聊 `g:<group_id>`，私聊 `p:<user_id>`（与撤回冷却键格式一致，见 `models.py::Target.key`）。

**理由**：避免 A 群的聊天摘要泄漏到 B 群，避免 A 群的破防影响 B 群的发言。

**与 I-25 的关系**：不是二选一。I-25 定「场景情绪必须分房」，I-26 定「分房的范围还包括计数器和记忆」，且「跨会话一致的整体心情由 `BotMood` 承担」——**不是共享 `UserState.emotion_current`**。

**代码现状（两项均 ❌，实测）**：
- `auditor.py::SubconsciousAuditor._bump` `state = self._stimuli.setdefault(user_id, _Stimulus())`；`audit()` 签名（`auditor.py::SubconsciousAuditor.audit`）无 `chat_scope` → A 群连夸 3 次，B 群第一句就破防。
- `memory_router.py::LocalSQLiteProvider._init_schema` 建表只有 `user_id` 列，索引 `idx_mem_user ON memories(user_id, created_at)`；`engine.py::EmotionEngine.process` 存入的是原始消息全文 → **A 群聊天内容在 B 群被检索注入 prompt**（`engine.py::EmotionEngine.process`）。
- `grep -rn "chat_scope\|session_id" packages/ --include=*.py` → 零命中，两个词在代码里都不存在。

**术语统一**：原稿的 `session_id` 一律改称 `chat_scope`，与 I-25 及张力架构裁决书保持一致。

**出处**：#20 #21 #64

### I-27 乱序消息防御｜**细化**｜P0

**计划原文**（第 42 条）：「校验消息时间戳，旧消息到达时拒绝覆盖新状态」——方向已覆盖。
**增量（具体实现）**：

- `UserState` 增加 `arrival_timestamp`（毫秒）或 `sequence`（单调递增）
- 入口处：`if req.timestamp < state.last_event_ts: return {status: "stale", applied: False}`
- 比较时机：**在 `event_key` 去重之前**先比时间戳
- 日志：`[WARN] Out-of-order message dropped`

**为什么必须做**：HTTP 不保证顺序，网络抖动时旧消息晚到会用「过去的情绪」覆盖「现在的情绪」。
**出处**：#48 #46 #47 #41

### I-28 `event_key` 生成算法升级｜**修正**｜P0

**计划原文**（第 40 条）：「基于全局唯一 event_key 的数据库校验」——只说了要有，没说怎么生成。
**决议**：`event_key = hash(user_id + merged_text + batch_absolute_ts_ms)`，**不能只用 `user_id + text`**。
**保留**：15s 的 `EVENT_KEY_WINDOW` 作为**兜底防线**，不作为唯一防线。
**防碰撞**：毫秒级时间戳 + `user_id` + `batch_id` 多重哈希，防 1ms 内连发碰撞。
**出处**：#72 #48

### I-29 防抖队列冲刷与 event_key 的关系｜**边界**｜P1

**决议**：跨防抖窗口的两次冲刷生成**各自的** `event_key`——即使落在同一 15s 窗口内，底层字典也允许不同请求（因为队列已把它们当两次交互）。
**出处**：#72

### I-30 幽灵状态补偿（Compensate）｜**细化**｜P0

**计划原文**（第 21 条）：「降级发生时，异步通知核心机补录本次交互状态」——方向已覆盖。
**增量（接口契约）**：

- 新增 `POST /api/v1/compensate`
- 请求体：`{user_id, chat_scope, message, trigger_type, original_event_key}`
- **异步**调用，不阻塞用户回复
- 验收标准：Adapter 日志必须出现 `compensate request sent`，且 Core 数据库状态必须更新

**出处**：#48 #42

## 四、持久化与并发层（Increments 34–41）

### I-34 SQLite WAL 强制开启｜**细化**｜P0

**计划原文**（第 68 条）：「强制开启 `PRAGMA journal_mode=WAL;`，防多线程锁死」——方向已覆盖。
**增量**：`create_engine` **和** `memory_router` 的**裸连接**都必须加，不只 ORM 层：

```python
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=5000;
PRAGMA synchronous=NORMAL;
```

**为什么强调裸连接**：`memory_router.py` 的本地兜底用的是原生 `sqlite3.connect`，绕过了 SQLAlchemy，ORM 层设 PRAGMA 对它无效。
**出处**：#1 #49 #47

### I-35 本地异步写队列｜**纯新增**｜P1

**决议**：若 WAL 后写入仍频繁，引入 `asyncio.Queue` + 单消费者协程串行写，避免多协程抢锁导致 `database is locked` 阻塞主线程。
**边界**：队列有界（上限 1000），满时丢弃最低优先级写入（`MessageCount` 优先丢，`UserState` 不丢）。
**出处**：#48

### I-36 数据库物理隔离｜**细化**｜P0

**计划原文**（第 66 条）：「单独使用 memory.db 存储记忆」——已覆盖。
**增量**：明确三库分离——`app.db`（状态/Token/消息计数）、`memory.db`（记忆）、`persona_evolved.txt`（演化输出，非数据库）。

### I-37 记忆 TTL 与 LRU 参数｜**细化**｜P0

**计划原文**（第 64 条）：「7 天 TTL 与 200 条 LRU 淘汰」——已覆盖。

### I-56 人格极端化四道防线｜**纯新增**｜P1

## 十、防坑死线汇总（12 条，不可违反）

| # | 死线 | 违反后果 |
|---|---|---|
| D1 | 情绪机绝不向主 LLM 下达行为指令，只输出状态 | 抢夺宿主控制权，人格混乱 |
| D2 | 动态数据（OS/状态/记忆/时间）绝不进 System Prompt 前缀 | 前缀缓存击穿，成本飙升 |
| D3 | 时间戳只到分钟，绝不带秒 | 缓存永远不命中 |
| D4 | 规则硬拦截必须在概率解禁之前 | 解禁变成解除安全限制 |
| D5 | `override_directive` 必须在 Prompt 最末尾 | 破防指令无效，Bot 继续端架子 |
| D6 | 白名单判断必须是判定逻辑第一行 | 管理员被误扣分 |
| D7 | 性格参数必须持久化，不每轮读取 | 缓存破坏 + 延迟增加 |
| D8 | 所有内存计数器必须绑 TTL | 大群 OOM |
| D9 | `trigger_type` 必须在请求进入时确定 | 口径判错，理由完全相反 |
| D10 | 私聊 `group_id` 传 `None`，不传空字符串 | 键变成 `g:`，所有私聊共享冷却池 |
